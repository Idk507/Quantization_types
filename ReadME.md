# Quantization Execution Roadmap: From Fundamentals to Production Serving

## Introduction

This roadmap is written as an execution plan rather than a reference catalogue, meaning each phase specifies what to build, which tool to use, how long the phase realistically takes for a small team of one to three engineers, what the exit criteria are before moving to the next phase, and what evidence you should collect to defend the decision in a design review. The plan assumes the end goal is deploying a quantized large language model into a real serving environment with measurable latency, throughput, and cost improvements, validated against task specific accuracy rather than generic benchmarks alone. Treat the time estimates as engineering effort assuming access to appropriate GPU hardware and a representative evaluation dataset already exists; if either of those prerequisites is missing, add time to the corresponding phase to build them first, since the single most common cause of roadmap slippage in quantization projects is discovering mid project that no one has assembled a trustworthy evaluation set.

## Phase 1: Numerical Foundations and Baseline Measurement, roughly three to five days

The objective of this phase is to build the numerical intuition needed to interpret every result that follows, and to establish the unquantized baseline you will measure every later phase against. Concretely this means implementing affine quantization and dequantization by hand for a single weight matrix, as in the code example from the earlier reference document, so that scale, zero point, symmetric versus asymmetric, and per tensor versus per channel granularity stop being abstract vocabulary and become something you have manually computed and inspected. In parallel, stand up the baseline: load the target model in its native precision, typically BF16, on the target inference engine, whether that is vLLM, TensorRT-LLM, or a simpler Hugging Face transformers pipeline for early experimentation, and measure and record memory footprint in gigabytes, time to first token, inter token latency, maximum achievable batch size at your latency service level objective, and tokens per second per GPU at that batch size. Separately, run your task specific evaluation harness against the baseline model and record the score, since every quantization decision from this point forward will be judged against these numbers. The exit criterion for this phase is a written baseline report containing all of the above numbers plus the manually implemented quantization function passing a basic correctness check against a reference implementation such as PyTorch's native quantization ops.

## Phase 2: Weight Only Post Training Quantization, roughly one to two weeks

This phase produces your first deployable quantized artifact and should target four bit weight only quantization using AWQ as the primary method, given its speed and strong accuracy to effort ratio, with GPTQ run in parallel on the same model as a comparison point since the two methods occasionally diverge in which layers they handle well. Assemble a calibration set of a few hundred to a couple of thousand examples that are representative of production traffic, not generic web text, since calibration set mismatch is a common silent cause of underperforming quantized models. Run AutoAWQ and AutoGPTQ or GPTQModel to produce two candidate checkpoints, load each into your serving engine, and re run the full measurement suite from phase one: memory footprint, latency and throughput at your target batch size, and the task specific evaluation score. The exit criterion is a side by side comparison table of baseline, AWQ, and GPTQ across all measured dimensions, a decision on which quantized checkpoint to carry forward, and an explicit written statement of the accuracy delta versus baseline and whether that delta is acceptable for the product, escalated to product or research stakeholders if the answer is unclear rather than decided unilaterally by the engineering team.

## Phase 3: Activation and KV Cache Quantization, roughly one to two weeks, conditional

Enter this phase only if phase two's throughput or cost numbers are still insufficient and profiling confirms the workload is compute bound rather than memory bound, which typically shows up as GPU compute utilization near saturation at your target batch size with headroom still remaining in memory bandwidth. If that condition holds, implement SmoothQuant style W8A8 quantization using your serving engine's built in support, which both vLLM and TensorRT-LLM provide natively, and separately evaluate FP8 quantization if your GPU generation is Hopper or newer, since FP8 typically requires less calibration effort than INT8 and often matches or beats it in accuracy at equal bit width. Independently of whether activation quantization is applied, evaluate KV cache quantization to INT8 or INT4 if your product involves long context conversations or long document workloads, since KV cache memory frequently exceeds model weight memory at long sequence lengths and is a distinct decision from weight quantization. Run the full measurement suite again for each candidate configuration. The exit criterion is the same comparison table extended with the new candidates, plus a specific note on whether the added engineering complexity and accuracy risk of activation quantization was justified by the measured throughput gain, since it is entirely legitimate and common for this phase to conclude that weight only quantization from phase two was already sufficient.

## Phase 4: Fine Tuning Under Quantization, roughly one to three weeks, conditional

Enter this phase only if the product requires further training on top of the quantized or soon to be quantized model, for example domain adaptation or preference tuning, rather than pure inference deployment of an already capable base or instruction tuned model. Implement QLoRA style fine tuning with an NF4 frozen backbone and double quantization enabled, choosing adapter rank and target modules based on a small sweep rather than a single guess, since undertrained or under sized adapters are a common failure mode at this stage. Track training loss, validation loss, and the same task specific evaluation metric used throughout this roadmap at multiple checkpoints during training, not just at the end, to catch overfitting or capability regression early. The exit criterion is a fine tuned, quantization compatible checkpoint whose evaluation score meets or exceeds the target set in earlier phases, along with training curves and adapter configuration documented for reproducibility.

## Phase 5: Production Serving Integration, roughly one to two weeks

This phase moves the selected checkpoint from an experimental script into the actual serving stack that will handle production traffic. Concretely this means confirming your chosen inference engine has a fused, hardware optimized kernel for the exact quantization format you selected, since format support and kernel maturity vary meaningfully across engine versions and a mismatch here silently erases much of the expected speedup, then load testing across the realistic distribution of batch sizes, sequence lengths, and concurrent request patterns that production traffic actually exhibits rather than a single synthetic benchmark configuration, since the memory bound versus compute bound regime determines which format actually helps and that regime shifts with traffic shape. Configure autoscaling, request batching, and any KV cache management settings appropriate to the serving engine, and run a soak test of at least twenty four hours to catch memory fragmentation or slow leaks that short benchmarks miss. The exit criterion is a serving deployment that meets your latency service level objective under realistic load, with dashboards in place for GPU memory utilization, throughput, latency percentiles, and error rate.

## Phase 6: Rollout, Governance, and Observability, ongoing

This phase never formally ends and should be treated as a standing operating process rather than a project milestone. Before full cutover, run a canary or shadow traffic deployment where the quantized model serves a small percentage of real traffic or receives a mirrored copy of production requests, comparing its outputs against the full precision model on the same inputs to catch regressions that offline evaluation missed. Maintain a fixed, versioned evaluation suite that every future candidate checkpoint, whether newly quantized, retrained, or upgraded to a new base model, is required to pass before promotion, and keep the full precision checkpoint readily available with a fast rollback path for at least the first several weeks after cutover. Review production quality signals, whether explicit user feedback, implicit engagement metrics, or automated output quality classifiers, on a recurring cadence, since quantization induced degradation often concentrates unevenly on specific input types or edge cases that do not show up in an aggregate offline metric.

## Suggested Timeline Summary

For a team executing sequentially, phases one and two are mandatory and typically take two to three weeks combined and represent the highest return on effort in this entire roadmap. Phases three and four are conditional and should only be entered when profiling data or product requirements explicitly justify them, since skipping them when unnecessary is the correct engineering decision rather than a shortcut. Phase five typically takes one to two weeks and should not be compressed, since production load testing is where most quantization related incidents are caught before they reach real users. Phase six is not a phase with an end date but the ongoing discipline that determines whether the quantization investment continues to pay off as the model, traffic, and product evolve over time.

# All Types of Quantization, Step by Step

Step 1, Uniform Affine Min Max Quantization. This is the starting point for everything else. A tensor is mapped to integers using a scale, and optionally a zero point if the distribution is not centered at zero. Symmetric quantization forces the zero point to zero and is simpler and faster, asymmetric quantization allows an offset and is more accurate for distributions that are not centered, such as activations after a ReLU. Learn this first because every later technique is a refinement of this same core operation.

Step 2, Granularity Choices: Per Tensor, Per Channel, Per Group. Once you understand the basic operation, the next decision is how many scale factors to use. Per tensor uses one scale for an entire matrix and is cheapest but least accurate. Per channel assigns one scale per output neuron or filter and is the default in almost every serious toolkit today. Per group, also called group wise, splits a row into small blocks such as 32, 64, or 128 elements each with its own scale, and is the granularity used by GPTQ, AWQ, and GGUF.

Step 3, Dynamic Quantization. This is the simplest deployable technique, where activation scales are computed on the fly at inference time from the actual input, with no calibration dataset required. It is fast to apply and commonly used for RNNs and simple linear layers, but is generally less accurate than static calibration based methods for larger transformer models.

Step 4, Static Post Training Quantization, PTQ, with Calibration. Here you run a small representative dataset through the model once to observe activation ranges, then fix the scale factors before deployment, using a statistical criterion such as KL divergence minimization or percentile clipping rather than raw min max to avoid outliers dominating the range. This is the standard technique for classical CNNs deployed through TensorRT, ONNX Runtime, or TensorFlow Lite.

Step 5, Quantization Aware Training, QAT. This introduces simulated quantization, called fake quantization, into the forward pass during training or fine tuning, so the model learns weights that are robust to rounding error, using the straight through estimator to let gradients pass through the non differentiable rounding step. Learn this after PTQ because it is more expensive and is only necessary when PTQ alone does not meet your accuracy bar.

Step 6, Mixed Precision Quantization. Instead of a single bit width for the whole network, this assigns different bit widths to different layers based on a sensitivity measure, commonly the top eigenvalue or trace of the loss Hessian, as in HAWQ, so sensitive layers stay at higher precision and flat, forgiving layers go as low as two or three bits. This is a natural next step once you understand that not all layers tolerate quantization equally.

Step 7, LLM.int8(), Outlier Decomposition. The first technique built specifically for large transformer quantization. It identifies a small number of systematic outlier feature dimensions in activations, computes those in FP16, and computes the remaining vast majority of the matrix multiply in INT8, a mixed precision decomposition rather than a single global scheme.

Step 8, GPTQ, Hessian Based Weight Only PTQ. This reframes weight quantization as a layerwise second order optimization, quantizing one column at a time and updating remaining unquantized weights in that layer to compensate for the error just introduced, using an approximate inverse Hessian from a calibration set. This is the technique to learn for reaching four bit and three bit weight only quantization with strong accuracy retention.

Step 9, AWQ, Activation Aware Weight Quantization. A faster alternative to GPTQ that does not require backpropagation. It identifies which weight channels matter most based on the magnitude of their corresponding activations, then rescales those salient channels before quantization using a mathematically equivalent transformation. Learn this alongside GPTQ since the two are usually compared directly on the same model.

Step 10, SmoothQuant, Weight and Activation Quantization for W8A8. This solves the harder problem of quantizing both weights and activations to INT8. It offline migrates quantization difficulty from hard to quantize activations into easy to quantize weights using a per channel smoothing factor that can be fused into adjacent layers at export time, at zero runtime cost.

Step 11, ZeroQuant. An extension of the weight and activation quantization line of work that adds fine grained group wise quantization plus a lightweight layer by layer knowledge distillation step to recover accuracy without a full training pipeline.

Step 12, SpQR, Sparse Quantized Representation. This pushes weight only quantization below four bits by explicitly detecting a small set of outlier weights per layer and storing just those at full precision in a separate sparse structure, while the dense remainder is compressed aggressively. This is the weight side counterpart to the outlier isolation idea from LLM.int8().

Step 13, QuIP and QuIP#, Incoherence Processing. These target the extreme low bit regime, two bits and below, by first applying a random orthogonal or Hadamard rotation to weights before quantization, spreading concentrated information across many coordinates so the result quantizes more like a Gaussian. QuIP# adds a lattice codebook vector quantizer on top for further accuracy at two bits.

Step 14, AQLM, Additive Quantization for LLMs. This generalizes vector quantization by representing groups of weights as a sum of vectors drawn from multiple learned codebooks, currently one of the strongest published results for two bit and lower average bit width compression.

Step 15, OmniQuant. This introduces a small number of learnable clipping and equivalent transformation parameters optimized block by block on a calibration set with lightweight gradient descent, giving a single flexible framework that works for both weight only and weight plus activation settings.

Step 16, Rotation Based W4A4, QuaRot and SpinQuant. These generalize the incoherence processing idea into a full pipeline for quantizing both weights and activations to four bits, applying Hadamard rotations at multiple points including within attention. SpinQuant improves on QuaRot by learning the rotation matrices rather than using fixed random ones.

Step 17, HQQ, Half Quadratic Quantization. A calibration free method that solves a robust optimization problem in closed form per layer with no dataset or backpropagation required, useful when no representative calibration data exists or quantization must happen at load time.

Step 18, KV Cache Quantization. A distinct scope from weights and activations, this compresses the key and value tensors cached during autoregressive decoding, typically to INT8 or INT4, and becomes critical at long context lengths where the KV cache can exceed the size of the model weights themselves. KIVI is a representative technique here.

Step 19, FP8 Quantization, E4M3 and E5M2. Rather than integers, this keeps a floating exponent at low bit width, which handles dynamic range better than INT8 at the same bit budget and is natively accelerated on Hopper and newer GPU generations for both training and inference.

Step 20, Microscaling Formats, MXFP4 and MXFP6. These quantize small blocks of values with a shared exponent scale, standardized by the Open Compute Project, letting four bit and six bit floating point formats approach eight bit accuracy, and are supported on the newest generation of accelerators.

Step 21, QLoRA, Quantization for Fine Tuning. This freezes a backbone in a four bit format called NF4, information theoretically optimal for normally distributed weights, adds a second quantization pass over the quantization constants themselves called double quantization, and trains small low rank adapters in BF16 on top, backpropagating through the frozen quantized weights with the straight through estimator. Learn this once you need to train, not just serve, under a constrained memory budget.

Step 22, GGUF and K Quants. An engineered family of mixed bit width group wise schemes used by llama.cpp, assigning different average bit widths to different tensor types within a transformer based on measured sensitivity, and the dominant format for local CPU and consumer GPU inference due to excellent memory mapped loading.

Step 23, Binary and Ternary Quantization. The most extreme point on the spectrum, restricting weights to two or three discrete values and replacing multiply accumulate with bitwise operations. Historically BinaryConnect and XNOR Net, revived at scale by BitNet b1.58, which trains transformer language models from scratch with ternary weights rather than quantizing an already trained model after the fact.

Step 24, Quantization Native Pretraining. The final and most advanced step, where the model is trained from initialization in low precision, such as FP8 pretraining recipes used at large AI labs, or in a quantization native parameterization like BitNet, producing models that are robust to low precision by construction rather than corrected for it after training.

This ordering moves from the mathematical core outward to increasingly specialized and aggressive techniques, and mirrors the execution roadmap discussed earlier: fundamentals first, then weight only PTQ, then weight plus activation PTQ, then fine tuning under quantization, then extreme compression, and finally quantization native training as the most advanced endpoint.
